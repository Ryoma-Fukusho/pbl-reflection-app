# プロンプト設計

今のプロンプト（`PROMPT_VERSION = "v10"`）が何を・なぜそう設計しているかをまとめる。
文面の正本は [lib/prompts/v10.ts](../lib/prompts/v10.ts)、組み立ては [lib/conversation.ts](../lib/conversation.ts)、
ステージのねらいは [lib/stage-guide.ts](../lib/stage-guide.ts)。版ごとの変遷は [history.md](./history.md)。

**導入実験は未実施。** ここに書くことは設計上の理由であって、効果の裏付けではない（§8）。

---

## 1. 設計が満たすべき要請

| # | 要請 | 設計への帰結 |
|---|---|---|
| R1 | 内省を深める問いを出す | ALACT モデルと質問会議に沿ったステージ（§3） |
| R2 | 参加者間で条件を揃える | ステージの順序はサーバーが決める。入口と出口の問いは固定文言（§2） |
| R3 | 集めたデータがどの条件で得られたか追える | プロンプト版・モデル・effort を全レコードに記録する（§7） |

R1 と R2 は引っ張り合う。問いを学習者に合わせて変えるほど深まりうるが、そのぶん参加者ごとの刺激が揃わなくなる。
本システムは「骨格（ステージの順序と、入口・出口の問い）は固定し、その内側の問いの文面を学習者の発話に合わせて生成する」形でこれを解いている。

## 2. 固定と生成の切り分け

| 発話 | ステージ | 固定/生成 | DB の `generated` |
|---|---|---|---|
| 開始の問いかけ（問題提示） | `problem` | 固定文言 | `false` |
| 問い | `fact` / `feeling_other` / `essence` | 生成 | `true` |
| 締めの問い | `closing_insight` | 固定文言（型は共通で、本人の最初の問題を差し込む） | `false` |
| 締めの問いの直前の受け止め | `closing_insight` | 生成 | `true` |
| 次に試すことの問い | `action_plan` | 生成 | `true` |
| Try（行動計画の整理） | `try_plan` | 生成 | `true` |

- **開始の問いかけ**: 質問会議と同じく問題提示から入る。回答は評価で比べる「最初の問題」なので、全参加者に同じ問いを出す（比べる2つの回答がどちらも共通の問いへの答えになる）
- **締めの問い**: 回答（`closingInsight`）が主な分析対象。生成にすると、回答の差が内省の差なのか問いの差なのか分けられない
- **締めの問いの直前の受け止め**: 締めの問いだけを出すと、直前に話した大事な話に一言も触れずに話題が変わり、聞いてもらえなかった感じが残る（試用で「せっかく話したのに無視されてさみしい」と言われた）。受け止めは別のメッセージとして生成し、締めの問いの文面は変えない
- **次に試すこと**: 質問会議ではアクションプランを問題提示者自身が出す。LLM に行動計画を作らせず本人に問う。評価では使わないので固定せず、締めの答えを受け止めて会話の流れで聞く（例や候補は挙げない）
- **振り返りの振り返り**: 質問会議の最後の手順。どの問いが考えるきっかけになったかを本人が言葉にしておくと、次に一人で振り返るときに自分にその問いを向けられる（学会の質疑「自分で深掘りする力はつくか」への対応）。対話の流れに入れると、終わりに決まった問いが続いて手続きのように感じるので、Try の後に任意の入力欄として置く

質問会議でも問題提示から始め、良かったことのような前置きは置かない。率直に話せるかは場の設計（普段のメンバーと別の組み合わせ）で担保している（舘野ら 2015）。本システムでは、プロジェクトにかかわる人に共有しないことがそれにあたる。

締めの問いは、質問会議の「問題の再定義」と同じく、本人の最初の問題を前にして聞く。文面の型は全参加者で共通にし、本人が最初に書いた問題をそのまま差し込む（システムが作った文は入らない）。

> 最初に「（本人の最初の問題）」と話してくれました。ここまで問いに答えてきて、その問題は、いまどう見えていますか？

- **新しい問題を出すことを求めない**。「あらためて、いまの問題は何か」と聞くと、新しい本当の問題を作ることを促してしまい、対話の途中で LLM が差し出した言葉を借りて答えやすくなる（締めの回答に LLM 由来の言葉が混ざると、評価で本人の内省の深まりと区別しにくくなる）。また、問題が変わらなかった人や、問題ではなくなった人の答える場所がなくなる
- **原因をどこに見るかは問いの側で指定しない**。自分に向けることを前提にすると、回答が自己に向いても内省の結果なのか迎合なのか分けられず、原因が本当に外にある場合にまで自責を促すおそれがあるため

次に試すことの問いも、問題があることを前提にしない。

## 3. 理論との対応

### 3.1 ALACT モデル

コルトハーヘンの ALACT モデル（行為 → 行為の振り返り → 本質的な諸相への気づき → 行為の選択肢の拡大 → 試行）の局面に、ステージを対応させている。
システムが担うのは第2〜4局面で、第1局面（行為）は PBL の活動そのもの、第5局面（試行）は次の活動にあたる（試行が次のサイクルの行為になる、という点は原典で要確認）。
対応と各ステージのねらい（進め方 B で、これが語られたら次へ進む）は [lib/stage-guide.ts](../lib/stage-guide.ts) にあり、画面の「振り返りの進み方」にも同じものを出している。

| ステージ | 局面 | ねらい |
|---|---|---|
| （PBL の活動） | 第1局面 行為 | システムの外 |
| `problem` | 第2局面 行為の振り返り | 引っかかっていること・モヤモヤしていることが語られた（初期入力。1回で進む） |
| `fact` | 第2局面(自分の側) | その場面で自分が何をし、何を考え、どう感じたかが本人の言葉で語られた |
| `feeling_other` | 第2局面(相手の側) | 相手の側に立った想像が本人の言葉で語られた（相手の様子の観察だけでは足りない） |
| `essence` | 第3局面 | 本人が本当は何を望んでいたかが、報告ではなく気づきとして語られた |
| `closing_insight` | 第3局面 | （固定文言） |
| `action_plan` | 第4局面 行為の選択肢の拡大 | （生成。1回で答える） |
| （次の PBL 活動） | 第5局面 試行 | システムの外 |

第2局面を自分の側と相手の側に分けているのは、ALACT モデルの第2局面が自分と相手の双方の行為・思考・感情・望みを問うことに基づく（原典で要確認）。

### 3.2 質問会議

| 質問会議の手続き | 本システムでの実装 |
|---|---|
| 助言を禁止し、質問だけで進める | `COMMON_SYSTEM` の助言禁止と「答えを示唆する問いをしない」。Try でも新しい助言を足さない |
| ファシリテーター（ALC）は中身に介入せず、進行だけを扱う | 進め方 B のファシリテーター判断（§5） |
| 他者の視点から問題を捉え直す | `feeling_other` |
| 問題提示から始める | 開始の問いかけ（`problem`） |
| 最後に問題を本人の言葉で言い直す（問題の再定義） | 締めの問い |
| アクションプランは問題提示者が出す | 次に試すこと（`action_plan`）を本人に問う |
| 最後に会議そのものを振り返る | 振り返りの振り返り（Try の後の任意の入力欄） |

### 3.3 ステージの順序

- `fact` を `feeling_other` より前に置く。事実を思い出す前に解釈を尋ねると、出来事が都合のよい物語に整えられたまま固まるため
- `feeling_other` は他者視点に焦点を置く。他責的な問題認識を崩す鍵になるため

## 4. 問いを出すときのふるまい（`COMMON_SYSTEM`）

細かい禁止を積み上げると、問いが機械的になる（「ほかに浮かんだことはありますか？」のような尋問めいた問いが続いた）。素の LLM との違いは細かい制約ではなく、質問会議の手順という骨格の側にあると考え、研究の骨格として固く守ることだけを書き、それ以外の話し方は LLM に任せている。

**必ず守ること**

- 解決策や助言を言わない。答えを示唆する問いも、質問の形をした助言なので言わない（質問会議の規則）
- 相手や、相手の判断・行動を評価しない。根拠のない褒め言葉も、観点を示して良い面を挙げることも含む（学会で「LLM は褒めるだけ」と指摘された点。肯定されると考え直す理由がなくなり、他責の見方まで認めてしまう）。話してくれたことへの受け止めや感謝はよい
- 対話を終えることや、次へ進むことを言わない（進行はシステムが持つ）
- 返答の最後に、本人が考えを進めるための問いを1つ置く

**任せること**

- 受け止め方、返答の長さ、問いの立て方
- うまく言葉にできていないことを仮の言葉にして差し出すこと。決めつけず、本人に確かめる形にする（言語化を助けるため）

## 5. 進め方ごとの組み立て

### 進め方 A（各ステージ1ターン）

system に `COMMON_SYSTEM` + `STAGE_INSTRUCTIONS[stage]` + 最初の問題を入れ、会話の先頭に前提文脈（最初の問題とメモ）を1ターン置いて、ステージの問いを1つ生成させる。

### 進め方 B（ファシリテーターの判断を経る）

各ターンで LLM を2回呼ぶ。質問会議の ALC（進行）とメンバー（問い）の分担にあたる。

1. **判断**（`FACILITATOR_SYSTEM`。JSON で返させる。中身には介入しない）
   - `focus`: 学習者がいま扱っている問題の一文。学習者が自分から根本へ話を移したら、移った先にする
   - `thread`: いちばん掘る価値のある学習者の言葉（強い気持ち、繰り返し、価値や願いが表れた言葉）
   - `flow`: `on_track`（順調）/ `learner_shift`（学習者が自分から話を移した）/ `drifting`（それている）/ `shallow`（浅いまま）
   - `level`: ステージのねらいに対して `not_yet`（まだ触れていない）/ `report`（出来事の報告にとどまる）/ `insight`（本人の解釈・気づきとして語られた）
   - `stage_done`: `insight` なら true。ターン数が目安（`STAGE_TURN_BUDGET`）を超えていて、ねらいに近いことが語られていれば `report` でも true
2. **進むか留まるか**（サーバーが決める）: `stage_done` か、学習者が「次の観点へ」を押したら次のステージへ。それ以外は留まる。ただし Problem は初期入力なので、判断によらず1回で進む（下記）
3. **問い**（`COMMON_SYSTEM` + `facilitatedQuestionInstruction`）
   - ステージに入るとき: 進め方 A と同じ `STAGE_INSTRUCTIONS` に、観点が変わることの一言を足す
   - `drifting`: 力ずくで戻さず、いま話していることと `focus` のつながりを学習者に尋ねる。1つのステージで1回まで。2回目以降は付いていく
   - `shallow`: 聞き直さず、ねらいに向けて答えやすい具体的な問いにする
   - それ以外: `thread` を手がかりに、ねらいに向けて掘り下げる
   - ステージごとの注意（`STAGE_CAUTIONS`）を毎回添える。例: `feeling_other` は主語を問題の場面の相手にし、相手が学習者をどう見ていたか・何を望んでいたかを尋ねる、`essence` は「どうしてほしかったか」と聞かない

判断は assistant メッセージの `facilitation` に残す。画面には、いま扱っている問題といま掘っている話を出し、話の状態・ねらいへの到達・理由は `?debug=1` のときだけ出す。

### Problem は初期入力で、掘り下げない

Problem は状況を入力する場であって、問題を確定させる場ではない。ここで問いを重ねると、後のステージ（事実・相手の視点・本当の願い）で扱う内容と重なり、評価で比べる「最初の問題」もシステムに形を整えられたものになる。このシステムは問題の形を多角的に見て学びを深めるものなので、問題の所在が後のステージで変わるのはかまわない（ファシリテーターの `focus` が追いかける）。

### 自動で次へ進む論拠

- **進行は問題提示者ではなくファシリテーターが持つ**: 質問会議では、ALC が会議の進行と学習過程にだけ介入し、問題提示者は自分の問題に答えることに集中する（舘野ら 2015）。進むかどうかの判断を学習者に任せると、この分担と逆になる
- **記述の状態を判定して支援を変える先行研究がある**: 丸山・森本は振り返りの記述を「事実の想起」「気づきを伴う振り返り」「教訓に至る振り返り」に機械学習で分類し、段階に応じて振り返りプロンプトを変え、最後の段階ではプロンプトを出していない。`level` の report / insight はこれにならう
- **判定は外れる前提で作る**: 丸山・森本の分類は適合率 69.9%・再現率 67.7%。外れたときのために学習者の「次の観点へ」を残し、判定がいつまでも終わらないときのためにターン数の目安を置く（質問会議でも明確化は時間の目安で区切る。舘野らの表2では20分）
- **深さで区切ること自体は質問会議からは言えない**（質問会議は時間で区切る）。この点の根拠は丸山・森本の側にある

## 6. Try（行動計画）

Try は、本人が「次に試すこと」として答えた内容を、本人の言葉のまま整理したものと定義している。行動計画は本人が出す（質問会議のアクションプランの提示）。対話中に助言を禁じている以上、最後に LLM が行動計画を足すと「結局 LLM が答えを出している」ことになるため。

- 本人が言っていない行動を作らない
- 「〜してほしかった」という他者への要望を、「〜を伝える」のような本人の行動に書き換えない
- 3項目以内。答えが乏しければ1〜2項目
- `- ` で始まる行だけ。見出しや太字は使わない（画面は Markdown を描画しない）

## 7. 生成パラメータと再現性

| 項目 | 値 | 記録先 |
|---|---|---|
| モデル | `claude-sonnet-5`（`CLAUDE_MODEL`） | `sessions.model`, `messages.model` |
| effort | `medium`（`CLAUDE_EFFORT`） | `sessions.effort` |
| プロンプト版 | `v10` | `sessions.promptVersion`, `messages.promptVersion` |
| アプリ版 | コミット SHA の先頭7桁 | `sessions.appVersion` |

- Claude Sonnet 5 には temperature が無い。effort は思考の量の指定で、出力のばらつきを抑えるものではない。応答は決定的にならない
- 文面を変えたら `PROMPT_VERSION` を上げる。過去の版のファイルは残していないので、必要なら git（タグ `ver1` など）から取り出す

## 8. 主張できること・できないこと

**主張できる（設計として）**

- 質問会議の手順（問題提示・明確化・再定義・アクションプラン・振り返り）と規則（助言禁止・進行と中身の分担）を LLM の制約として形式化し、一人で実行できる形にした
- ALACT モデルの局面に沿ったステージを、サーバー側で決まった順に進める
- 評価で比べる2つの問い（開始の問いかけと締めの問い）を、全参加者で共通の型にし、`generated` で固定文言と生成文を機械的に分けられる
- 会話履歴の正本をサーバー側に置き、LLM への入力と記録が一致する
- プロンプト版・モデル・effort・トークン数・レイテンシを全レコードに記録する

**主張できない**

- 内省が深まる、といった効果（導入実験が未実施）
- プロンプトが意図どおり動くこと（出力制約の遵守率を測っていない）
- 応答の安定性（同じ入力での応答のばらつきを測っていない）

## 9. 未決着の論点

- **判定と評価の循環**: 進め方 B はステージのねらいが「報告」でなく「気づき」として語られたら進み、評価では Problem への回答と締めの回答を上田の分類（報告・解釈…）でコーディングする。内省が深まるように設計した以上、評価でもそう出るのは当然で、出なければ設計が失敗している、という前提として受け入れる。締めの問いは固定文言で、押さずに1回で答えさせている
- **判定の精度**: 判断はすべて `facilitation` に残っているので、導入実験の後に人のコーディングと照合して精度を測れる
- **内省の分析の枠組み**: 上田のリフレクションの4つの分類と原因の帰属先の2つの軸で、評定者2名がコーディングし κ 係数を報告する計画。帰属先が自己に向いたことを「良い」と読まないようにする
- **出力の遵守**: 「最後に問いを1つ」は指示だけで、生成後の検証はしていない（v9 の試用で、1ターンに問いが2つ並ぶことがあった）
