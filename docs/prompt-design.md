# 対話版（`/`）プロンプト設計

最終更新: 2026-09-10 / 対象: `PROMPT_VERSION = "v2"`（v1 からの差分は §10）

このドキュメントは **対話版（コルトハーヘンの ALACT モデルに沿った6ステージ対話）のプロンプト設計だけ**を対象に、
「何を・なぜそう設計したか」を実装から逆算して明文化したもの。学会発表の設計パートの原稿の元になる。

- **ルート構成**: 対話版が既定の体験で **`/`**。統制群の **KWS フォーム版は `/kws`**。
  旧 `/session` は `/` へ転送する（[app/session/page.tsx](../app/session/page.tsx)）
- 実装の正本は [../lib/prompts/v2.ts](../lib/prompts/v2.ts)（文面）と [../lib/conversation.ts](../lib/conversation.ts)（組み立て）
- システム全体の設計は [design.md](./design.md)（2026-08 時点の計画。ルート構成などは本ドキュメントが上書きしている）
- **予備実験は未実施**。したがって本ドキュメントの主張は全て「設計上の論理」であり、経験的裏付けではない（§8）

## 1. 設計が満たすべき要請

プロンプト設計は「良い問いを出す」だけでは決まらない。この研究では次の3つが同時に効いている。

| # | 要請 | 由来 | 設計への帰結 |
|---|---|---|---|
| R1 | **内省を深める問いを出す** | 研究目的そのもの | 理論（ALACT・質問会議）に沿ったステージ列（§3） |
| R2 | **参加者間で条件を統制する** | 群間比較を成立させるため | 進行をサーバーが固定 / 主要な問いは固定文言（§4.2, §5.2） |
| R3 | **収集データの再現性を担保する** | 論文の「データの信頼性」節 | プロンプト版・モデル・effort を全レコードに刻む（§6） |

R1 と R2 は緊張関係にある。**適応的に問いを変えるほど内省は深まりうるが、その分だけ参加者ごとの刺激が揃わなくなる。**
本システムはこの緊張を「**骨格は固定し、肉付けだけ生成させる**」という形で解いている。これが設計上の中心的な判断。

## 2. 全体構造：固定と生成の切り分け

1セッションで学生が受け取るAIの発話は7つ。そのうち **AIが自由に生成するのは4つだけ**。

| 順 | 発話 | ステージ | 画面上の表示 | 生成/固定 | DB上の `generated` |
|---|---|---|---|---|---|
| 1 | 開始の問いかけ | `keep` | 良かったこと | **固定文言** | `false` |
| 2 | 問い | `problem` | 気になったこと | 生成 | `true` |
| 3 | 問い | `fact` | 事実 | 生成 | `true` |
| 4 | 問い | `feeling_other` | 相手の視点 | 生成 | `true` |
| 5 | 問い | `essence` | 本当の願い | 生成 | `true` |
| 6 | 締めの問い | `closing_insight` | 本当の課題 | **固定文言** | `false` |
| 7 | Try（行動計画） | `try_plan` | — | 生成 | `true` |

学生の発話は6ターンで、**全参加者で必ず6ターン**になる（[types.ts](../lib/types.ts) の `DIALOGUE_STAGES` と
[messages/route.ts:88-125](../app/api/sessions/%5BsessionId%5D/messages/route.ts#L88-L125) がサーバー側で駆動）。
画面上の表示名は [dialogue-workspace.tsx](../app/dialogue-workspace.tsx) の `STAGE_LABELS` にあり、
ステージ識別子（DB に入る値）とは別に持っている。

### なぜ入口と出口を固定文言にしたか

- **1（開始）** — 学生の発言がまだ無いので生成の材料が無い。かつ全参加者の入り口を一字一句揃えられる。
- **6（締め）** — この問いへの回答 `closingInsight` が**内省の深さを測る主要データ**になる。
  ここを生成にすると、問いの表現が参加者ごとに変わり、**回答の差が「内省の差」なのか「問いの差」なのか分離できなくなる**。
  「全参加者に一字一句同じ問いを提示した」と論文に書けることが、測定の妥当性の前提になっている。

この切り分けは DB に `generated: boolean` として記録され、分析時に固定文言と生成文を機械的に分離できる。
コード上も [`FIXED_MESSAGES`](../lib/prompts/v2.ts#L41) という1つのオブジェクトにまとめてあり、
「AI に書かせない文言」がどれかがファイルを見るだけで分かる。

## 3. 理論的枠組み

### 3.1 ALACT モデルとステージ列の対応

Korthagen の ALACT モデル（行為 → 行為の振り返り → 本質的諸相への気づき → 行為の選択肢の拡大 → 試行）を、
対話の6ステージに写像している。

| # | ステージ | 引き出すもの | ALACT 上の位置 |
|---|---|---|---|
| 1 | `keep` | うまくいったこと・続けたいこと | 行為(1)の想起の入口。**肯定から入る** |
| 2 | `problem` | 引っかかったこと・モヤモヤ | 振り返り(2)の対象場面の特定 |
| 3 | `fact` | その場面で実際に何をしたか | 振り返り(2) — **事実の想起**。解釈と分離する |
| 4 | `feeling_other` | 相手から自分の行動がどう映っていたか | 振り返り(2) — **脱中心化** |
| 5 | `essence` | 本当はどうしたかったのか（願い・目的） | 気づき(3)への移行 |
| 6 | `closing_insight` | **自分が主体的に向き合うべき本当の課題** | 気づき(3)の**言語化・確定**（測定点） |
| — | `try_plan` | 次回の具体的行動 | 行為の選択肢の拡大(4) |
| — | （次回のPBL活動） | — | 試行(5)。システムの外 |

### 3.2 質問会議の手続きをプロンプト制約として実装している

本システムのプロンプトは、**質問会議（アドバイスを禁じ、問いだけで進める手続き）を LLM の制約として実装したもの**
と位置づけられる。具体的には次の3点が対応する。

| 質問会議の手続き | プロンプト上の実装 |
|---|---|
| アドバイス・解決策の提示を禁じる | `COMMON_SYSTEM` の「解決策やアドバイスを絶対に教えないこと」＋ Try 生成での「新しい助言を追加してはいけない」（§5.5） |
| 他者の視点を持ち込んで問題を捉え直させる | `feeling_other` ステージ（§5.3） |
| 最後に問題を本人の言葉で言い直させる | `closing_insight` の固定文言（§5.2） |

**この対応づけが本研究の中心的な主張になる。**
「AIに内省を促させた」ではなく「**対面の質問会議で人間のファシリテータが担う手続きを、
LLMのプロンプト制約として形式化し、一人でも実行できる形にした**」という立て方の方が、
効果検証を伴わない現段階でも成立する。

### 3.3 ステージ順序の論拠

- **`fact` を `feeling_other` より前に置く** — 事実の想起を済ませる前に感情や解釈を尋ねると、
  出来事が「自分にとって都合のよい物語」に整形されたまま固定される。ALACT が(2)を独立した段階として置くのはこのため。
- **`feeling_other` で他者視点に絞る** — 他責的な問題認識を崩す最大の鍵が脱中心化であるため。
  v1 では「自分の感情」と「相手からの見え方」の両方を尋ねていたが、v2 で他者視点に一本化した（§10）。
- **`closing_insight` を ALACT の外に追加している** — これは理論からの要請ではなく**測定上の要請**。
  (3)の気づきを本人の言葉で1箇所に集約させ、コーディングの対象を明確にする。
  発表では「理論由来のステージ」と「測定のために足したステージ」を区別して説明すること。

## 4. プロンプトの層構造

Claude への1回のリクエストは、次の3層で組み立てられる（[conversation.ts:54-72](../lib/conversation.ts#L54-L72)）。

```
┌─ system ───────────────────────────────────────────┐
│  ① COMMON_SYSTEM        全ステージ・全条件で共通    │  ← ふるまいの制約
│  ② STAGE_INSTRUCTIONS[stage]                       │  ← このターンの役割
│  ③ 現在の Keep / Problem                            │  ← 状態の再掲
└────────────────────────────────────────────────────┘
┌─ messages（会話履歴）──────────────────────────────┐
│  user     : buildContextText(keep, problem, memo)  │  ← ④ 前提文脈を先頭に1ターン
│  assistant: 開始の問いかけ（固定文言）               │
│  user     : 学生の回答                              │
│  assistant: 生成された問い                          │
│  ...（Firestore から読んだ履歴をそのまま）           │
│  user     : 直前の学生の回答                         │
└────────────────────────────────────────────────────┘
```

Try 生成のときだけ ② が `TRY_PLAN_INSTRUCTION` に差し替わり、履歴の末尾に `FINAL_USER_PROMPT` が付く。
**①と②の連結は [conversation.ts](../lib/conversation.ts) 側で行い、プロンプト定義ファイルには
連結済みの文字列を置かない。** どのターンでも「共通の制約 + そのターンの役割」という同じ形になる。

### 4.1 履歴はクライアントではなくサーバーが組む

`messages` に入る履歴は **Firestore から読み出したもの**であり、クライアントから送られてこない
（クライアントが送るのは `{ content, composeMs, memo }` だけ）。
これは主にデータの信頼性のための設計だが、**プロンプト設計上も意味がある** ——
「AIに渡された文脈」と「DBに残っている記録」が定義上ズレない。
再現性の議論（§6）が成立するのはこの構造が前提。

### 4.2 進行の制御をLLMに委ねていない

「次にどのステージへ進むか」は LLM の判断ではなく、[types.ts](../lib/types.ts) の `nextStage()` による決定的な遷移。
LLM は **与えられたステージの問いを1つ作る**ことしか担当しない。

- 利点：全参加者のターン数・問いの種類・順序が完全に揃う（R2）。離脱ステージの集計も可能になる。
- 代償：学生が浅い回答をしても対話は先に進む。**深さに応じた追い込みができない**。
  これは既知の代償であり、統制を優先した設計判断として明示的に主張する（§7-1）。

## 5. 各構成要素の全文と設計意図

### 5.1 COMMON_SYSTEM — ふるまいの制約

[v2.ts:24-31](../lib/prompts/v2.ts#L24-L31)。全ステージ・両条件に共通で載る。**v1 から変更なし。**

```
あなたは評価者や指導者ではなく、PBLを行う学生の深い内省を引き出す優れたファシリテーターです。
学生に具体的な解決策やアドバイスを絶対に教えないこと。
相手を否定せず、共感的で受容的なトーンを保つこと。
返答は日本語で、200字程度までに収めること。
箇条書きや見出しを使わず、話し言葉に近い自然な文章で返すこと。
問いかけは必ず1つだけにすること。複数の質問を並べないこと。
```

制約ごとの意図：

| 制約 | 意図 |
|---|---|
| 評価者・指導者ではない / 解決策を教えない | **これが実験操作の核であり、質問会議の手続きそのもの**。AIが答えを出した時点で、内省ではなく助言受領の体験になる |
| 否定せず受容的 | 心理的安全性。否定されると学生は失敗場面の開示をやめ、`problem` 以降が全て機能しなくなる |
| 200字程度 | AIの発話量が学生の発話量を上回ると、対話の主導権が移る。`totalUserChars` / `totalAssistantChars` を別々に記録しているのはこれを事後確認するため |
| 箇条書き・見出しを使わない | 箇条書きは「整理された助言」の形式であり、話し言葉より受け手を受動的にする |
| 問いは必ず1つ | 複数問うと学生は答えやすい方だけを選ぶ。**答えにくい問い（＝深い問い）が回避される** |

### 5.2 FIXED_MESSAGES — AI に書かせない2つの発話

**開始の問いかけ**（[v2.ts:46](../lib/prompts/v2.ts#L46)、v1 から変更なし）

```
今日のPBL活動、おつかれさまでした。この時間は、あなたの中にあるものを一緒に言葉にしていく時間です。
まずは、うまくいったこと・続けたいと思ったことから聞かせてください。
```

- 「あなたの中にあるものを一緒に言葉にしていく」＝ **この場が助言の場ではないことの宣言**。
  COMMON_SYSTEM でAI側の振る舞いを縛るのと対に、学生側の期待値も最初に設定している。
- 肯定的な問いから入るのは、いきなり失敗を問われることによる防衛的反応を避けるため。

**締めの問い**（[v2.ts:62](../lib/prompts/v2.ts#L62)、**v2 で変更**）

```
ここまでの対話、ありがとうございました。最後にひとつお聞きします。
今日の対話を通して、あなた自身が主体的に向き合うべき『本当の課題』は何だと改めて思いましたか？
```

- 「**今日の対話を通して**」＝ 対話前から持っていた考えではなく、対話によって生じた変化を尋ねている。
- 「**あなた自身が主体的に向き合うべき**」＝ **回答を自省に着地させるための語句**。
  本研究が見たいのは「他責的な問題認識 → 自分ごと化された課題への捉え直し」であり、
  その終着点をこの一文が定義している。質問会議における「問題の言い直し」に対応する。
- 「**本当の課題**」＝ `essence` ステージで扱った願い・目的を踏まえた再定式化を促す。
  画面上のステージ表示も「本当の課題」に揃えてある。
- v1 は「気づき**や**、どんな**問題**があると改めて思いましたか」と、
  自己に向かう問いと外部に向かう問いの二択を許していた。回答の方向が分岐すると、
  コーディング結果が「内省の深さ」ではなく「どちらを選んだか」を反映してしまうため一本化した（§10）。

### 5.3 STAGE_INSTRUCTIONS — 実際に生成に使われる4つ

[v2.ts:73-98](../lib/prompts/v2.ts#L73-L98)。`keep` と `closing_insight` も定義はあるが**実行時には使われない**
（両者は `FIXED_MESSAGES` を使うため）。ステージ列との対応を崩さないためだけに置いてある。

**`problem`**（v1 から変更なし）

```
現在のステージは problem です。直前の学生の発言に短く共感を示したうえで、
今日の活動で引っかかったこと・モヤモヤしたことを尋ねる問いを1つだけ返してください。
```

→ **唯一「共感 → 問い」の二部構成を明示している**ステージ。Keep（肯定）から Problem（否定的経験）へ
話題を転回させる箇所なので、受容を明示的に挟ませている。

**`fact`**（v1 から変更なし）

```
現在のステージは fact です。学生が語った問題の場面について、そのとき実際に何が起き、
自分が具体的にどう動いたのかを思い出させる問いを1つだけ返してください。
評価や解釈ではなく、事実の想起を促すこと。
例: その時、あなたは具体的にどのように動きましたか？
```

→ 「**評価や解釈ではなく**」という否定形の制約が入っている唯一のステージ。
学生は問題を語る際にすぐ原因分析（＝解釈）に飛びやすく、それを一度事実に引き戻す役割。
v2 で `feeling_other` から感情の問いを外したため、**その場面での心情はこのステージの語り直しの中で
自然に現れる分に委ねる**という整理になっている。

**`feeling_other`**（**v2 で変更**）

```
現在のステージは feeling_other です。その場面において、
相手の側から見たときに自分の行動や状況がどう映っていたかに目を向けさせる問いを1つだけ返してください。
例: 相手から見ると、あなたの当時の行動はどう映っていたと思いますか？
```

→ **他者視点（脱中心化）に一本化した。**
v1 は「自身の感情**と**相手からの見え方の**両方**」を要求しており、
COMMON_SYSTEM の「問いかけは必ず1つだけ」と**プロンプト内部で衝突していた**。
質問会議において他責的な問題認識を崩す鍵は他者視点なので、そちらを残した（§10）。
なおステージ識別子 `feeling_other` は DB のスキーマ互換のため変更していない
（改名すると v1 で収集したデータとの対応が切れる）。
**論文・画面上の呼称は「相手の視点」で統一**しており、UI の `STAGE_LABELS` も変更済み。

**`essence`**（**v2 で微修正**）

```
現在のステージは essence です。出来事の表面的な不満ではなく、
その背後で本人が本当はどうしたかったのか（本質的な願いや目的）を引き出す問いを1つだけ返してください。
例: 本当は、あなたはその状況でどうしたかったのでしょうか？
```

→ 「行動の是非」から「その行動を駆動していた価値・願い」へ抽象度を上げる。ALACT(3)への移行点。
v2 で「表面ではなく」を「**表面的な不満**ではなく」と具体化した。不満の吐き出しで止まらせないため。

**各ステージに例文（`例: ...`）を置いている理由**

LLM は抽象的な指示だけだと問いの水準がターンごとにぶれる。例文は**問いの抽象度を固定する錨**として置いている。
副作用として例文がそのまま出力されやすくなるが、条件統制の観点ではむしろ許容範囲（§7-4 は保留中）。

### 5.4 前提文脈の注入

[v2.ts:159-166](../lib/prompts/v2.ts#L159-L166)。会話履歴の**先頭に user ロールで1ターン**挿入される。v1 から変更なし。

```
以下は振り返りの前提文脈です。以後の応答は必ずこの文脈を踏まえてください。
Keep: {keep or 未入力}
Problem: {problem or 未入力}
Memo: {memo or 未入力}
```

- ステージが進んで履歴が伸びても、Keep/Problem を見失わせないため。
- 加えて `systemInstruction` 側にも Keep/Problem を再掲している（意図的な二重掲載。§7-5 は保留中）。
- `Memo`（常設メモ欄）は学生が対話中いつでも書ける自由記述で、毎ターン上書き保存され、**毎回の生成にも入る**。
  対話の線形な流れから外れた気づきを拾う経路として設計されている。

### 5.5 Try 生成（**v2 で変更**）

[v2.ts:146-157](../lib/prompts/v2.ts#L146-L157)。両条件で共通。
`systemInstruction` は `COMMON_SYSTEM` に続けて次を載せる：

```
Turn FINAL です。AI から新しい助言や一般論の解決策を追加してはいけません。
これまでの対話の中で学習者自身が気づき、述べた内容（特に対話の終盤で語られた課題）および
メモ欄の内容を統合し、次回のPBLで本人が意識すべき具体的な行動計画（Try）として
再構成・要約して箇条書きで出力してください。
各項目は、学習者自身が対話の中で述べた内容に根拠を持つものだけにすること。
この出力に限り、箇条書きを使ってよい。
```

続けて履歴の末尾に user ロールで以下を追加してから送る（[conversation.ts:111](../lib/conversation.ts#L111)）：

```
これまでのチャット履歴とメモを踏まえて、次回のPBLで意識する Try を箇条書きで整理してください。
新しい助言を加えず、学習者自身が対話の中で述べた内容だけを材料にしてください。
```

- **v1 の論理的な穴を塞いだ箇所。** v1 は対話中だけ助言を禁じ、最後に AI が行動計画を提示していたため、
  「結局 AI が答えを出しているのでは」という指摘に**実装で反論できなかった**。
- v2 では Try を「**新規の助言ではなく、学習者自身の発話の再構成・要約**」と定義し、
  (i) 新しい助言・一般論の追加禁止、(ii) 材料は本人の発話とメモのみ、
  (iii) 各項目が本人の発話に根拠を持つこと、の3点を明文化した。
  これで COMMON_SYSTEM の「解決策を教えない」と矛盾しなくなり、質問会議の手続きとも整合する。
- 「この出力に限り、箇条書きを使ってよい」は COMMON_SYSTEM の制約の明示的な解除。
  対話中は話し言葉、成果物は一覧性、という使い分け。
- **両条件に等しく適用される**（KWS フォーム版の Try も同じプロンプトで生成される）。
  Try の質が群間差の交絡要因にならないよう、ここは揃えている。
- 「対話の終盤で語られた課題」という表現にしているのは、KWS フォーム版には `closing_insight` ステージが無いため。
  条件によらず成立する言い方にしてある。

## 6. 生成パラメータと再現性

| 項目 | 値 | 記録先 |
|---|---|---|
| モデル | `claude-sonnet-5`（`CLAUDE_MODEL` で上書き可） | `sessions.model`, `messages.model` |
| effort | `medium`（`CLAUDE_EFFORT` で上書き可） | `sessions.effort` |
| プロンプト版 | `v2` | `sessions.promptVersion`, `messages.promptVersion` |
| アプリ版 | コミットSHA先頭7桁 | `sessions.appVersion` |

- **temperature は使えない。** Claude Sonnet 5 / Opus 5 では `temperature` と `top_p` が廃止されており、
  送るとリクエストが 400 で弾かれる。Gemini 版で `temperature: 0.2` が担っていた「問いの表現の揺らぎを
  抑え、参加者間の刺激を近づける」役割（R2）に**直接対応するパラメータは Claude には無い**。
- 代わりに記録・統制するのが `effort`（`low` / `medium` / `high` / `xhigh` / `max`）。
  ただしこれは**思考にどれだけトークンを使うかの指定**であって、出力のばらつきを抑えるものではない。
  上げるほど品質・費用・応答時間がすべて増える。既定を `medium` にしているのは、生成物が
  「問い1つ」か短い Try であり、参加者を待たせる時間が体験そのものに含まれるため。
- したがって**応答は決定的にならない**（§8）。これは Gemini 版でも同じだったが、
  揺らぎを抑える役割は今や COMMON_SYSTEM の出力制約（200字程度・問いは1つ・箇条書き禁止）だけが
  担っている。**低温度で統制している、という説明はもう使えない。**
- assistant メッセージ1件ごとに `latencyMs` / `usage`（トークン数）/ `finishReason` も記録される。

### 版の切り替え方（実装）

呼び出し側は全て [../lib/prompts/index.ts](../lib/prompts/index.ts) 経由で参照している。
版を上げる手順は：

1. 現行版をコピーして `vN.ts` を作り、`PROMPT_VERSION` を上げる
2. `index.ts` の再エクスポート先を差し替える
3. 本ドキュメントの §10 に差分と根拠を書く

`index.ts` を差し替えるだけで済むのは、新しい版が現行版と同じ export を持つ場合。
**プロンプトの構造自体を変えるなら呼び出し側も直すことになるが、それは正しい変更であって避けるべきものではない。**
文面や構造の改善を「差し替えの手数」のために我慢しないこと。

**過去の版のファイルは書き換えないこと。** 書き換えると、収集済みデータの `promptVersion` が
どの文面を指すのか追えなくなり、分析が破綻する。`v1.ts` は当時の文面の記録として残してあるだけで、
現在はどこからも読まれていない。

## 7. 設計上の論点と、その決着

添削で決着した項目（**採択**）と、まだ決めていない項目（**保留**）を分けて記録する。
保留項目は実験実施前に決めきること。

### 採択済み

#### 7-3. 締めの問いを自省に一本化した ✅ v2 で反映

- **問題**: v1 は「気づき（自己に向かう）」と「問題（外部に向かう）」の二択を許していた。
  `closingInsight` は内省コーディングの主対象なので、**回答の方向が分岐すると測定の妥当性が崩れる**。
  外部の問題を述べた回答が低く判定されても、それは内省の浅さではなく問いの設計に起因しうる。
- **決定**: 「あなた自身が主体的に向き合うべき『本当の課題』」への着地に一本化（§5.2）。
- **根拠**: 本研究の核心は「他責的な問題認識から、自分ごと化された課題への捉え直し」であり、
  終着点を問い自体が定義している方が、主張と測定が一致する。

#### 7-2. `feeling_other` を他者視点に一本化した ✅ v2 で反映

- **問題**: 「自身の感情」と「相手からの見え方」の両方を要求しており、
  COMMON_SYSTEM の「問いかけは必ず1つだけ」と**プロンプト内部で矛盾していた**。
  出力が2問になるか片方に寄るかのどちらかで、参加者間でばらつく。
- **決定**: 他者視点（脱中心化）に絞る（§5.3）。感情の想起は `fact` の語り直しに委ねる。
- **根拠**: 質問会議において他責化を打ち破る最大の鍵は他者視点であり、こちらを残す方が理論的に一貫する。
- **副次的な効果**: 1ステージ＝1つの認知操作、という対応がきれいになった。UI の表示名も「相手の視点」に変更済み。

#### 7-6. Try 生成を「再構成・要約」と定義し直した ✅ v2 で反映

- **問題**: 対話中は助言を禁じているのに、最後に AI が行動計画を出す。
  「結局 AI が答えを出しているのでは」という指摘に実装で反論できなかった。
- **決定**: 新しい助言・一般論の追加を明示的に禁じ、材料を本人の発話とメモに限定した（§5.5）。
- **根拠**: 質問会議の手続きを最後まで貫くため。実装で裏付けられる主張になった。

#### 7-1. 深さによらず1ターンでステージが進む設計を維持する ✅ 現状維持

- **問題**: 「なるほど」の一言でも `fact` が終わったことになる。浅い回答への追い込みが無い。
- **決定**: **変更しない。** 統制を優先した設計判断として明示的に主張する。
- **発表での言い方**: 「本研究は設計報告・プロトタイプ提案の段階であり、
  統制群との比較および参加者間のデータ再現性を担保するため、
  **全参加者でターン数と問いの構造を厳密に固定する**設計判断を行った」。
- **注意**: 深掘りを入れるとターン数が参加者間で変動し、`turnCount` を統制変数として使えなくなる。
  将来入れる場合は「ステージ数は固定、ステージ内ターン数は可変」と分析の単位を整理し直すこと。
- **追記（2026-10-27, v3）**: ゼミで「6ターンは短い」と指摘されたため、進め方 B（ステージ内ターン数を学習者が決める）を
  **進め方 A と並べて**実装した。どちらを導入実験で使うかはゼミ内の試用で決める。下の「v2 → v3」を参照。

#### 7-8. 統制群との差分を「対話的スキャフォールディング」として定式化する ✅ 記述方針として採択

- **統制群（`/kws`、KWS フォーム版）** — 一人で静的フォームに入力する環境。
  問いは事前に固定されており、**他者の視点が入る契機がなく、他責的な記述のまま完結しうる**。
- **実験群（`/`、対話版）** — 非公開の対話空間で、AI が質問会議的な手続き
  （アドバイス禁止・他者視点の問い・課題の言い直し）を用いて介入する環境。
- 検証するのは「**単なる入力フォーム vs 対話的スキャフォールディング**」という差分によって、
  振り返りの記述がどう深化するか。
- **先に述べておくべき事実**: KWS フォーム版の Turn 1/2/3 の指示文の例文は、対話版の
  `fact` / `feeling_other` / `essence` と**同じもの**を使っている
  （[v2.ts:108-125](../lib/prompts/v2.ts#L108-L125)）。
  つまり両群は「問いの中身」ではなく「**進行の構造と、そこに至る文脈の作り方**」で差がついている。
  隠すと突かれるが、「問いを揃えたうえで構造だけを操作した」と言えれば**交絡が減る方向の主張材料**になる。
- なお KWS フォーム版のプロンプトは v1 から一切変更していない。動かすと群間差の解釈が濁るため。

#### 7-9. 用語を確定した ✅ 反映済み

- 統制群のフォームの呼称は **KWS** に統一（コード・ドキュメント・UI すべて反映済み。
  DB のフィールド名 `keep` / `problem` / `tryPlan` と `condition: "form"` は
  スキーマ互換のため変更していない）。
- 内省コーディングの枠組みとして **Kember et al. (2000) は使用しない**（原本が入手できず、
  本研究の文脈ともずれるため）。**代替の枠組みと出典の確定は保留**（§7-10）。

### 保留（実験実施前に決めること）

#### 7-10. 内省コーディングの枠組みの確定 🔶 未決着【最優先】

- Kember は不採用と決まったが、**代わりに何で内省の深さを判定するかが未確定**。
  候補として「上田のリフレクション4分類」が挙がっている。
- **やること**: 採用する枠組みと出典（原本にあたれるもの）を確定させる。
  併せて、評定者2名でのコーディングと κ 係数の報告という手続きを維持するかを決める。
- `closingInsight` がコーディングの主対象になるので、**枠組みが決まらないと §7-3 の一本化が
  正しい方向だったかを検証できない**。ここが決まって初めて測定計画が閉じる。

#### 7-4. ステージ名と例文が出力に混入しうる 🔶 未決着

- **現状**: 指示文に「現在のステージは fact です」という内部識別子が入る。また各ステージに例文がある。
- **懸念**: 前者は稀にAIの発話に漏れる（「fact の段階として伺いますが…」）。
  後者は例文がほぼそのまま出力されるため、実質的に**半固定文言として機能している**可能性がある。
- **やること**: 実データで、生成された問いが例文とどれだけ一致しているかを測る。
  一致率が高いなら「適応的な生成」という主張は弱くなる（が、条件統制の主張は強くなる）。
  **どちらを主張の柱にするか先に決める。**
- 選択肢: (a) ステージ名を出力に含めないよう明示 (b) 例文に「そのまま使わないこと」と付記
  (c) 逆に固定文言に寄せ、生成は共感部分のみに限定

#### 7-5. Keep/Problem が二重に注入されている 🔶 未決着（実害は小）

- **現状**: `systemInstruction` の末尾と、履歴先頭の前提文脈ターンの両方に同じ Keep/Problem が入る。
- **懸念**: 実害は小さいが、説明が重複しており発表で問われると答えにくい。
- 選択肢: (a) どちらかに寄せる (b) 現状維持し「重要文脈の冗長化は意図的」と明記する

#### 7-7. 出力制約の遵守を検証していない 🔶 未決着（推奨あり）

- **現状**: 200字・問い1つ・箇条書き禁止はいずれも**指示のみ**で、生成後の検証もリトライも無い。
- **推奨**: 予備実験なしで学会に出す以上、**遵守率を実測して報告する方が誠実**で、実装リスクも無い。
  `charCount` は記録済みなので事後集計できる。
- 代替案: 文字数超過・「？」複数・行頭記号を検出したら1回だけ再生成する

## 8. 現時点で主張できること／できないこと

予備実験を経ずに発表する以上、ここを混同しないことが最大の防御になる。

**主張できる**

- 質問会議の手続き（アドバイス禁止・他者視点・課題の言い直し）を **LLM のプロンプト制約として形式化**し、
  一人で実行できる形にした設計
- ALACT モデルを固定ステージ列として実装し、進行をサーバー側で決定的に制御する設計
- 測定点（開始・締め）を固定文言にすることで、参加者間の刺激を統制した設計
- Try を「新規の助言」ではなく「学習者自身の発話の再構成」として定義し、
  対話中の助言禁止と論理的に整合させた点
- 会話履歴の正本をサーバー側に置くことで、プロンプト入力と収集ログの一致を構造的に保証した点
- プロンプト版・モデル・effort・トークン数・レイテンシを全レコードに刻む再現性の設計
- `generated` フラグによる固定文言と生成文の機械的分離

**主張できない（言わない）**

- 内省が深まる／統制群より優れている、といった効果に関する主張
- プロンプトが意図どおり機能しているという主張（出力制約の遵守率も未測定）
- 応答の安定性（**測っていない**。同一入力での応答分散は未検証。加えて Claude では temperature による揺らぎの抑制自体ができない）
- v2 が v1 より良いという主張（**設計上の整合性を高めただけで、比較はしていない**）

**発表で先回りして述べるべき限界**

- 未検証であること（[todo.md](./todo.md) の段階3・4は実データ未通過）
- 深さによらずステージが進む設計（§7-1 — 統制を優先した判断として述べる）
- 群間差が複合介入によること（§7-8）
- 内省の深さの測定枠組みが未確定であること（§7-10）

### LLM を Gemini から Claude に変更（2026-09-09）

**プロンプトの文面は1文字も変えていない。** したがって `PROMPT_VERSION` は `v2` のまま。
変わったのは「誰に渡すか」と「どう渡すか」だけ。

| 項目 | 変更前 | 変更後 |
|---|---|---|
| モデル | `gemini-2.5-flash` | `claude-sonnet-5`（`CLAUDE_MODEL` で上書き可） |
| 呼び出し | Gemini REST を `fetch` で直接 | 公式 SDK `@anthropic-ai/sdk`（ストリーミングで受けて最終メッセージを取る） |

| 統制パラメータ | `temperature: 0.2` | `effort: "medium"`（§6） |
| AI 側の role | `model` | `assistant` |

書けたが、Claude Sonnet 5 / Opus 5 では temperature 自体が API から消えているため、この説明は使えない。

（[todo.md](./todo.md) の段階3が未検証）、旧名との互換は取っていない。

### v2 → v3（2026-10-27）

学会発表（2026-10-24）の質疑とゼミの指摘を受けた変更。`PROMPT_VERSION` を `v3` に上げた（`v2.ts` は書き換えていない）。

| # | 対象 | v2 | v3 | 根拠 |
|---|---|---|---|---|
| 1 | 締めの固定文言 | 「あなた自身が主体的に向き合うべき『本当の課題』は何だと改めて思いましたか」 | 「ここまで問いに答えてきたことを通して、あらためて、いまの問題は何だと思いますか」 | 質問会議の「問題の再定義」（問題提示者が、質問されたことを通してあらためて現在の問題は何かを提示する）に寄せた。v2 は自己への帰属を問いの側が前提にしており、迎合と自責化のおそれがあった（§7-3 の決定を改めた） |
| 2 | `STAGE_INSTRUCTIONS.closing_insight` | （未使用）「主体的に向き合うべき課題を尋ねてください」 | （未使用）「あらためていまの問題は何だと思うかを尋ねてください」 | 固定文言との整合 |
| 3 | `FOLLOWUP_INSTRUCTIONS` / `followupInstruction()` | なし | 追加 | 進め方 B で「この話を続ける」を選んだときに、同じステージの観点の中で掘り下げる問いを生成させる。前の問いを繰り返さない・別の観点に移らないことを指示 |

**進め方（`sessions.turnMode`）**

- `fixed`（進め方 A）: 従来どおり各ステージ1ターン、計6ターン
- `flexible`（進め方 B）: 発話のたびに「この話を続ける」「次の問いへ進む」を学習者が選ぶ。1ステージ最大 `MAX_TURNS_PER_STAGE = 5` ターン。締めの問いは1回で答える
- 開始画面で学習者が選ぶ。ステージの順序はどちらもサーバーが管理する
- 進め方 B で同じステージに複数回答えた場合、`sessions.keep` / `sessions.problem` には改行でつないで全て入る
- v3 より前のセッションには `turnMode` が無く、読み出し時に `fixed` とみなす

**画面の変更**

- システム名を「DeepReflect」から「振り返りアシスト」に変更
- 締めのステージの表示名を「本当の課題」から「問題の言い直し」に変更

**変更していないもの**: `COMMON_SYSTEM`、開始の固定文言、`problem` / `fact` / `feeling_other` / `essence` の指示、Try 生成、KWS フォーム版のプロンプト

### v3 → v4（2026-10-27）

開発者自身が進め方 B で一周した対話（実際のプロジェクトの内容、否定的・短い回答を含む）で、問いかけが崩れた。崩れ方と対応は次のとおり。`PROMPT_VERSION` を `v4` に上げた。

| # | 崩れ方（実例） | 対応 |
|---|---|---|
| 1 | 褒める・良い意味づけをする（「気まずさを感じながらも最後まで居続けられた」「大きな発見ですね」「責任を果たせた証」） | `COMMON_SYSTEM` で評価的な言葉と良い意味づけを禁止。受け止めは相手の言葉を短く言い換える1文まで |
| 2 | 気持ちを推測して言い当てる、仮定を重ねる（「もしそれが次に活かせる気づきだとしたら…」→「？？？？何を言ってるの？」） | 推測・解釈し直しを禁止。問いは平易に短く、仮定を重ねない。意味が通じなかったら謝って具体的な問いに変える |
| 3 | 直前の発言だけを追い、Problem の問題（雑に振られたタスク）から脇道（人前で画面を開きにくい）へずれる。本当の願いと締めの問いも脇道について問うことになった | `fact` / `feeling_other` / `essence` と掘り下げの指示で、対象を「Problem として挙げた問題の場面」に固定。脇道に入ったら戻す |
| 4 | 「覚えてない」「特段なんも」「さっき話したやん」を受け止めず聞き直す。手の動きや作業ペースを尋ねる | 短い答えは受け止めて次へ進むよう促す。答え済みの内容を聞かない。`fact` で細部を尋ねない |
| 5 | Keep で困ったことを話しても良い面を探させる | Keep の掘り下げで、良かったことが無い・困ったことを話した場合は「次の問いで聞く」と伝えて次へ促す |
| 6 | `feeling_other` が相手の表情を尋ねる／`essence` が「どうしてほしかったか」と相手への要求を尋ねる | 相手から見た自分の映り方を尋ねる、本人がどうしたかったかを尋ねる、と明記 |
| 7 | Try が5項目、本人の言っていない行動（「確認してから返事をする」）を足す、`**` の太字がそのまま表示される | 3項目以内、言っていない行動を作らない、締めの答えが乏しければ1〜2項目、`- ` の行だけで装飾なし |
| 8 | 相手の口調につられてくだけた口調に変わる | です・ます調で統一 |

同じ種類の回答を流す再現スクリプトで、1〜7 が出なくなることを確認した（実 API、2026-10-27）。

**コードの変更**: 進め方 B の user メッセージに `choice`（`continue` / `advance`）を記録する。上限で次へ進めたのか本人が選んだのかを後から区別するため。上限に達したステージでは送信ボタンを「次の問いへ進む」にし、「この観点で話せるのはここまでです」と表示する。
